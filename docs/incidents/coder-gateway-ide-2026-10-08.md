# Frequent Coder 503 and unavailable IDE, 2026-10-08

The Coder control-plane Pod remained Running, Ready, and without container restarts. The public Caddy gateway nevertheless logged 73 `no upstreams available` HTTP 503 responses over three hours on uc-k8sp4. Its shared Envoy reverse proxy used `unhealthy_status 5xx`, `max_fails 1` and `fail_duration 10s`: an application HTTP 500 or 502 withdrew the entire shared upstream. Normal optional Coder API errors could therefore remove the remaining healthy proxy paths and make unrelated pages return 503. Application/control-plane liveness was also being used as the shared gateway health probe.

An isolated test with the actual host Caddy version (2.11.4) reproduced the failure: two application HTTP 500 responses were followed by HTTP 503 on a healthy page. The fixed configuration returned the application errors without withdrawing the upstream and served the next healthy page with HTTP 200.

The TLS/GitOps reconciliation now owns the canonical gateway health directives. It excludes application status codes from passive transport-failure classification and probes Envoy's independent direct-response route. Three failed probes are required for withdrawal and two passes for recovery. TCP failures still participate in passive detection. Terraform published the source and Argo CD reconciled both public gateways; Caddy process IDs were retained.

Separately, Reverse's code-server was no longer listening on port 13337, while its workspace and Coder agent remained alive. The old template started it as an unsupervised background process. Available logs did not establish why the process exited; the incident must not be reported as a confirmed OOM or Pod failure. The IDE was restored with a detached, single-instance supervisor that restarts unexpected exits. This was installed using exec without restarting the workspace Pod or running Codex sessions. The supervised startup template was validated and activated. Reverse uses that active template on the next start; its current build was not changed.

Verification: the actual VS Code workbench rendered on three consecutive navigations, including the user's app URL. Across 198 browser requests, there were no HTTP 502/503 responses; one optional application API still returned HTTP 500 without poisoning gateway availability. Sixty probes across both origins and both custom/canonical hostnames returned HTTP 200. The gateway logged zero `no upstreams available` errors during the subsequent ten-minute check. Code-server's health endpoint and Coder's application health recovered. The workspace kept Pod UID `ac7b4213-344a-446a-9d17-9cd3b1b0f48c`, with zero restarts. An isolated supervisor test verified restart after repeated unexpected exits and single-instance enforcement.
