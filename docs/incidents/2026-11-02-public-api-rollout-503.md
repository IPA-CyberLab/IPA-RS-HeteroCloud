# 2026-11-02 公開 API の更新中に発生した 503

## 影響

HeteroCloud の Identity Center 対応を本番反映した際、公開ホームページへの監視で一時的な HTTP 503 を観測した。最初のロールアウトを含む監視期間は 138 回中 2 回が 503 だった。終了待機の対策を導入する次のロールアウトでも、旧 Pod の入れ替え中に 103 回中 4 回が 503 となった。後者は 12:30:38〜12:30:41 UTC に連続して発生し、応答には `no healthy upstream` が含まれていた。これらはサンプル監視の回数であり、全ユーザーへの影響件数ではない。

## 調査

12:30:37 UTC に 2 台目の旧 API Pod の終了が始まり、直後に上記の 503 が発生した。公開ゲートウェイは headless Service の DNS を使って API Pod を選び、その DNS 応答の TTL は 30 秒だった。旧 API Pod には、Pod 削除後に DNS・ゲートウェイへの反映を待つための終了前待機が設定されていなかった。ゲートウェイの正常な接続先が一時的になくなったことは応答から確認でき、旧 Pod の終了と新しい接続先の認識の時間差が原因候補である。ゲートウェイの当該時刻の詳細アクセスログは取得できず、2 つの 503 事象の全原因を断定できていない。

この時点では uc-k8sp4 がオフラインで、API は希望数 3 に対し 2 レプリカ稼働していた。ローリング更新ではそのうち 1 レプリカずつ入れ替えた。

## 対応と検証

API の Pod 終了時、まず 35 秒間リクエストを処理し続けて DNS とゲートウェイの更新を待ち、その後アプリケーションの最大 30 秒の graceful shutdown ができるよう終了猶予を 75 秒に変更した。チャートは Helm のレンダリングテストと GitHub Actions で検証し、Terraform と Argo CD で適用した。

本番で API Pod を 1 台ずつ正常終了させ、EndpointSlice と DNS の切り離し、旧 Pod の待機中の応答、新 Pod の起動、公開 URL の連続応答を確認した。1 台目は 77 回、2 台目は 83 回、計 160 回のリクエストがすべて HTTP 200 で、最も遅い応答は 0.771 秒だった。これは確認時点・対象経路のテスト結果であり、全種類の障害時の可用性を保証するものではない。
